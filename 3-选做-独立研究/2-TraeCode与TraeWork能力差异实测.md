# 实验2 · TraeCode 与 TraeWork 能力差异实测

> 实验方法说明：同一开发任务（"复现 hello_world 并多端运行、修环境、交 Git"）的
> **TraeCode 侧数据来自本机本次作业全程实测**（2026-09-23，所有数字可在本文与
> 仓库提交记录中溯源）；**TraeWork 侧基于官网 www.trae.cn/work 公开能力清单**
> 做对照推演，未在本机实测，已在表中明确标注"（官方文档）"。
> 结论只陈述有证据支撑的部分。

## 一、两侧执行同一任务的实际/推演过程

| 环节 | TraeCode（本机实测） | TraeWork（官方文档推演） |
|------|----------------------|--------------------------|
| 入口形态 | IDE 内嵌智能体（Trae 编辑器侧栏 + 内联终端），与代码工程同工作区 | 独立 AI 办公平台：Web 端 work.trae.cn + 桌面客户端，Work/Code/Design 三模式切换（官方文档） |
| 读文档 | 直接解析本地 docx（zip+XML），30 秒内产出任务清单 | 官方主打多格式文件理解（JSON/PPTX/CSV 等），上传后分析（官方文档） |
| 环境安装 | 直接在本机执行 20+ 条命令：定位 SDK、替换 cmdline-tools、装 NDK/系统镜像、建 AVD | 官方定位含终端与文件操作能力，可执行同类操作；但文件落在其云端 Workspace 为主，接管本机系统级目录不如本地 IDE 直接（推演） |
| 编码调试 | 逐行注释 main.dart → `flutter analyze` 验证零问题；改代码即改工程内文件 | Code 模式对应同类能力（官方文档），具体到本机 Android 工程的 Gradle 级修复未见公开基准（推演） |
| 多任务并行 | 单会话串行为主，重型构建期间可后台并行 2 个任务（实测：模拟器构建与镜像实验并行跑完） | 依托云端算力主打多任务并行（官方文档）；云端并行不占用本机 CPU，但访问本机模拟器/截图需本地协同（推演） |
| 取证留痕 | 全屏截图由本机实际采集（doctor 全绿、两端运行、仓库页面），证据与提交一一对应 | 产物在 Workspace 面板展示、可评论迭代（官方文档）；本机级全屏取证需下载后自行归档（推演） |
| Git/GitHub | 直接操作本地仓库并推送 `lecture1` 分支 | Workspace 内文件管理（官方文档）；推送需其云端环境持有凭据或在本地拉回后操作（推演） |

## 二、实测结论（仅基于 TraeCode 侧真实数据 + 官方公开信息）

1. **本地系统级改造是 TraeCode 的主场**。本次作业最难的一段——坏掉的
   cmdline-tools 导致 doctor 与 Gradle 连锁失败——需要在**本机**读源码
   （flutter_tools 的许可校验逻辑）、替换系统目录、装 NDK，全程 TraeCode 一气呵成；
   这类深度依赖本机文件系统与终端的任务，是其"AI 原生 IDE"定位的直接体现。
2. **TraeWork 的差异化在"办公域"与"云端并行"**（官方文档）：PPT 生成、深度调研、
   多任务云端并行、多端协同验收，这些 TraeCode 不提供；反过来 TraeWork 的云端
   Workspace 模式操作本机 SDK/模拟器/截图取证，链路比本地 IDE 长。
3. **对本课程场景的建议**（依据 4.1 节课程定位）：环境安装、案例复现、作业开发
   属于"本机工程 + 本机构建 + 本机取证"型任务，TraeCode/TraeWork Code 模式更顺手；
   文档撰写、跨设备查看进度的场景可用 TraeWork。两者账号体系同源（TRAE），
   第 5 周起按课程指引上手 TraeCode 精细编码即可无缝衔接。
