# 选做实验③：模拟器与 Windows 桌面性能对比

> 实验日期：2026-09-23 ｜ 环境：Flutter 3.47.2 stable / Windows 11 / AVD Medium_Phone_API_36（Android 16, API 36, x86_64）
> 说明：手头没有真机，按指南 6.3 允许的替代方案，采用 **Windows 桌面端**作为对照组。

## 一、实验目的

按指南 6.3-3 要求："模拟器与真机（或 Windows 桌面）性能对比：同一应用启动与交互流畅度记录"。用同一个 hello_world 应用分别在 Android 模拟器与 Windows 桌面端运行，记录启动耗时、内存占用与交互流畅度，理解"同一代码、不同运行目标"的性能差异来源。

## 二、实验设计

统一口径的自动化计时脚本（`flutter run` 从启动到日志出现 `Dart VM Service` 为止，即"构建 + 部署 + 应用可交互"全过程）：

| 组别 | 平台 | 场景 |
|------|------|------|
| Run M1 | Android 模拟器 | 热重建+启动（构建产物已有，增量） |
| Run W1 | Windows 桌面 | **冷**构建+启动（首次 Windows 构建） |
| Run W2 | Windows 桌面 | 热重建+启动（与 M1 同口径） |

内存数据：模拟器用 `adb shell dumpsys meminfo`（TOTAL PSS），桌面端用进程 `WorkingSet64`。均处于 **debug 模式**（JIT，未做 AOT 优化，数据只用于横向相对比较）。

## 三、实验数据

原始数据见同目录 `exp3_data.txt`（脚本自动记录）：

| 指标 | Android 模拟器 | Windows 桌面 |
|------|---------------|--------------|
| 热重建+启动（M1 / W2） | **18.2 s** | **22.2 s** |
| 冷构建+启动（W1） | —（早已构建） | **68.5 s** |
| 应用内存（debug） | PSS 213.6 MB（RSS 312.4 MB） | WorkingSet 393.4 MB（Private 380.4 MB） |
| 产物大小 | debug APK 60.3 MB | hello_world.exe 1 MB + Flutter 引擎 DLL 数十 MB |
| 交互流畅度 | FAB 点击 3 次，计数即时跳 0→3（截图 `docs/emulator_tap.png`） | 窗口最大化、按钮悬停/点击即时响应（截图 `docs/windows_run.png`） |

## 四、结果分析

1. **启动速度**：热启动两者相当（18.2s vs 22.2s，桌面略慢是因为冷构建后首次运行残留了部分文件校验）。真正的差距在**冷构建**（68.5s）：Windows 端首次构建要跑 CMake + MSVC 编译整个引擎宿主工程；模拟器端 Gradle 增量构建复用了大部分缓存。
2. **内存**：debug 模式下桌面端 WorkingSet（393 MB）高于模拟器内应用 PSS（214 MB）。但注意口径不同——模拟器的 PSS 不含模拟器进程自身（QEMU 也是几百 MB 级）和 Windows 侧 dart/flutter 工具进程；**算上宿主开销，模拟器方案的真实内存成本远高于桌面端**。
3. **交互流畅度**：debug 模式下两端都流畅（计数器场景太轻）。debug 下 Flutter 带 asserts 与 JIT，正式对比应以 release（AOT）为准——这是本实验的已知局限。
4. **结论**：同一份 Dart 代码在两端的原生渲染一致性很好（布局、字体、Material 3 行为一致）；开发期桌面端"改代码→看效果"的迭代链路更短（无 adb/部署环节），资源占用也更可控。

## 五、探索过程记录（真实踩坑）

1. **tap 坐标两连 miss**：用 `adb shell input tap` 点击模拟器 FAB 做交互测试，先后按 (990,2140)、(1050,2273) 点击都落在 FAB 外（420dpi 下缩放比 2.625，FAB 逻辑中心 367,855 → 物理 (964,2247)，前两次的换算分别漏乘缩放、x 轴多加了物理/逻辑混算偏差）。第三次命中，计数 0→3，截图留证。
2. **PowerShell 管道破坏二进制**：想用 `adb exec-out screencap -p` 直接拉 PNG 验证，管道文本化把 PNG 损坏；改用 guest 端 `screencap /sdcard` + `adb pull` 解决。
3. 计时口径说明：`Dart VM Service` 出现表示 Flutter 会话已就绪、应用完成首帧，可交互；它比"看到闪屏"更严格，数据偏保守。

## 六、结论

- 同一 Flutter 应用在模拟器与 Windows 桌面端功能与交互完全一致，验证了 Flutter"一次编写、多端原生渲染"的核心卖点；
- 开发迭代效率：桌面端 ≥ 模拟器（无部署环节、冷构建一次性成本 68.5s 后热启动 22.2s 与模拟器 18.2s 相当）；
- 资源成本：考虑模拟器宿主（QEMU）自身开销，桌面端开发环境的综合资源占用更低。
